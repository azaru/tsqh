# Agent Instructions

## Read order

Before coding, read the current project overview in `README.md`, `STATUS.md`, the active specification
named by `STATUS.md`, and the design provenance section of `README.md`. Do not read
`STATUS-HISTORY.md` or superseded specifications unless the active assignment explicitly requires
historical evidence.

## Development contract

- Work only on the local active specification. Do not inherit provisional APIs from another
  checkout.
- Treat external design material recorded in local provenance as read-only evidence. This
  repository must remain self-contained and must not require another checkout.
- Keep every repository file, identifier, prompt, comment, test, and generated artifact in English.
- Use pnpm exclusively and keep one `pnpm-lock.yaml`.
- Target Node.js 22 or newer, ESM, and strict TypeScript.
- Prefer Node.js built-ins and a small number of explicit modules over framework infrastructure.
- Keep deterministic planning independent of filesystem, Git, processes, clocks, providers, and
  network access.
- The controller selects transitions. Agents and native commands only report outcomes.
- A bounded, sanitized result from one completed agent step may be supplied as context to the next
  configured agent step. It is untrusted data and cannot select a transition, widen write
  authority, override the exact task, or turn a native failure into success.
- Execute external commands as an executable plus argument array with `shell: false`. Never build
  interpolated shell commands from configuration or agent output.
- Forward non-default environment values only through a gate profile's explicit `environmentKeys`;
  never expose profile credentials to agent-provider processes.
- Validate configuration strictly and reject unknown properties, unknown references, invalid visit
  limits, missing transitions, and unreachable terminal behavior.
- Run only one action at a time. Version 0 has no concurrency, daemon, distributed lease, or remote
  executor.
- Treat nonzero gate exit status as failure. Missing, malformed, contradictory, or unauthorized
  output blocks; it never passes by inference.
- Native gates must not mutate the candidate. Compare Git snapshots around each gate and block on
  any Git-visible candidate-path change even when the command exits zero. Owned ignored reports may
  still be regenerated by their configured gates.
- Validate Git changed paths after every writing agent step against the role's allowed path
  prefixes. Never let an agent edit workflow policy to unblock its own run.
- Add behavioral tests for happy paths, configuration failures, transition order, agent failure,
  gate failure, repair success, repair exhaustion, unauthorized changes, and command-spawn errors.
- Update `STATUS.md` when the implementation state or blocker changes. Keep it concise: current
  position, verification, blockers, and next action belong there; detailed completed-increment
  evidence and superseded snapshots belong in `STATUS-HISTORY.md` and must not be treated as
  current evidence.

## Maintainer operations

### Local SonarQube

The checked-in [`infra/sonar/compose.yaml`](infra/sonar/compose.yaml) reproduces the localhost-only
SonarQube/PostgreSQL service and intentionally uses the shared Compose project name `tsqh-sonar`.
Its database values and scanner token are environment-only. Start or inspect it with values from a
private environment file:

```sh
docker compose --env-file /path/to/private-sonar.env --file infra/sonar/compose.yaml up --detach
curl --fail --silent http://127.0.0.1:9000/api/system/status
```

[`sonar-project.properties`](sonar-project.properties) selects project `azaru_tsqh_mvp`, while
[`sonar-policy.json`](sonar-policy.json) pins the approved host, dedicated strict gate, TypeScript
profile, and `PREVIOUS_VERSION` new-code identity. Workflows that configure the Sonar gate provide
its scanner invocation. Do not commit an environment file or token. A fresh server must reproduce
the exact identities in the completed specification.

The fail-closed Sonar wrapper checks three distinct kinds of remote evidence: `project_status`
proves the computed result is `OK` with ignored conditions disabled; the assigned gate and its
definition prove the exact eight approved conditions; and the project `main` branch response proves
its explicit `PREVIOUS_VERSION` new-code assignment. Conditions without computed measures may be
absent from `project_status`; they remain mandatory in the gate definition.

### Manual local Codex smoke

The simple workflow task deliberately writes only under `src/` and `test/`. Run the smoke only when
`codex --version` succeeds and `codex login status` confirms authentication. Use a disposable,
clean Git copy of this repository so the example agents cannot touch the development checkout:

```sh
pnpm tsqh run \
  --config workflows/simple/workflow.json \
  --workspace /absolute/path/to/disposable-clean-tsqh-copy \
  --task workflows/simple/task.md \
  --runs-root /absolute/path/to/disposable-run-store \
  --json
```

The disposable copy needs its dependencies installed, and its initial `git status --porcelain`
must be empty. Record the real result of the latest local smoke, including whether it ran, in
`STATUS.md`.

## Delivery report

Report exact changed files, commands, exit statuses, test totals, the demonstrated workflow trace,
remaining limitations, and blockers. Do not claim a real Codex smoke test passed unless it ran.
